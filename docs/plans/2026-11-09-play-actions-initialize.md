# 최초 AAB의 명시적 Actions 초기화

## 근거와 범위

기존 `check` 실행에서 WIF와 Play의 편집 생성·번들·APK·트랙 조회가 성공했고 등록 버전은 없었다. 따라서 `requires_first_console_upload`는 빈 목록에 대한 클라이언트의 안내이며 실제 업로드 거절 응답이 아니다. 공식 Edits 안내의 최초 Console 업로드 기준은 보존하되, 사용자가 요청한 Actions 직접 업로드를 한 번 명시적으로 시험한다.

## 구현

1. 수동 `initialize` 또는 검증된 main 커밋 제목의 독립 토큰 `[initialize-play]`로만 기존 정확한 main 소스·서명·네이티브·AAB·APK 검증을 재사용한다. 일반 자동 실행은 기존 `deploy`를 유지한다.
2. 빌드 전 `allocate-first`는 모든 API 목록이 빈 상태인지 확인하고 코드 14만 할당한다. 업로드 직전 동일 편집에서 다시 확인한다.
3. 고정 패키지 `com.hebi.livetranslate`의 코드 14를 내부 테스트 `draft`로만 업로드한다. 반환 버전·SHA-256을 확인하고 심사 전송 없이 검증·커밋한다. 기존 심사가 진행 중이면 중단한다.
4. 새 편집에서 번들 SHA-256과 내부 초안의 정확한 버전을 재조회한다. App Signing·약관·키 변경 API와 초기화 변수 쓰기는 수행하지 않는다.
5. 실패 단계·HTTP 상태와 허용한 canonical 오류 상태만 보고한다. 일반 배포·승격·등록정보 변경의 기존 초기화 제한은 유지한다.

## 검증

수동 main 조건, 중복·빌드 도중 등록 경쟁, 고정 버전·draft, 업로드 및 재조회 해시, 편집 정리, 오류 정보 제한, 초기화 변수 미변경을 테스트한다. 전체 Python 검사·actionlint·YAML·diff 검사를 통과한 뒤 정확한 Actions 실행으로만 실제 업로드 결과를 판단한다.
